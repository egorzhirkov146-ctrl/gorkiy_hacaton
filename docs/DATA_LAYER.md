# Слой данных: схема, репозиторий и поиск

Этот документ описывает часть проекта, которая отвечает за хранение записей, их выборку за период и поиск по естественному запросу. Документ также объясняет, как эту часть подключают остальные модули, потому что NLU-модуль, API и фронтенд работают с данными только через неё.

## Что делает слой данных

Слой данных хранит задачи, встречи и напоминания в SQLite, и он отдаёт их сервисному слою через два класса. Класс RecordRepository создаёт, читает, меняет и удаляет записи, а класс SearchRepository находит записи по фразе пользователя. Задание требует, чтобы ассистент сохранял данные между запросами и находил старые записи без точного совпадения формулировок, поэтому слой данных решает именно эти две задачи.

## Схема базы данных

Основная таблица records хранит все поля, которые перечисляет раздел "Хранение данных" задания, и к ним добавлены два поля, которые нужны для повторяющихся записей. Модель описана в файле backend/models/record.py, а тесты из файла tests/test_storage.py проверяют, что все колонки, индексы и триггеры действительно создаются.

| Колонка | Тип | Обязательна | Назначение |
|---|---|---|---|
| id | INTEGER | да | первичный ключ |
| user_id | INTEGER | да | владелец записи, по умолчанию 1 |
| type | VARCHAR(20) | да | task, meeting или reminder, значение проверяет CHECK |
| title | VARCHAR(500) | да | краткое название, которое не может быть пустым |
| raw_text | TEXT | нет | исходная фраза пользователя |
| datetime | DATETIME | нет | дата и время события в локальном времени, пусто у задачи без срока |
| created_at | DATETIME | да | момент создания записи |
| status | VARCHAR(20) | да | pending, done или cancelled, значение проверяет CHECK |
| recurrence | VARCHAR(16) | нет | правило повтора: daily, weekdays, weekly, monthly или yearly |
| recurrence_until | DATETIME | нет | последний день, до которого действует повтор |

Таблица record_embeddings хранит векторы для семантического поиска, и каждая её строка ссылается на запись через внешний ключ с ON DELETE CASCADE. Векторы лежат отдельно, потому что без библиотеки sentence-transformers эта таблица остаётся пустой, а основная таблица не растёт. Колонка text_hash содержит хеш SHA-1 от заголовка и исходной фразы, и по нему репозиторий видит, что текст изменился и вектор нужно пересчитать.

Виртуальная таблица records_fts содержит полнотекстовый индекс FTS5 по колонкам title и raw_text. Три триггера records_fts_ai, records_fts_au и records_fts_ad обновляют индекс при вставке, изменении и удалении записи, поэтому индекс остаётся точным даже тогда, когда другой модуль пишет в records напрямую через ORM. Вспомогательная таблица records_fts_vocab показывает словарь индекса, и поиск по опечаткам берёт из неё слова, которые есть в базе.

Даты хранятся в локальном времени без часового пояса, потому что парсер дат NLU-модуля возвращает именно такие значения. Колонка created_at хранится так же, чтобы сравнение даты создания с датой события не требовало перевода между зонами.

## Как создаётся схема

Функция init_storage из пакета backend/storage создаёт таблицы через SQLAlchemy create_all, затем добавляет недостающие колонки и индексы, а потом создаёт объекты FTS5. Функция init_db из backend/db.py вызывает init_storage при старте приложения. Мы выбрали create_all вместо Alembic, потому что за время хакатона схема меняется редко, а одна идемпотентная функция проще в поддержке, чем каталог миграций.

База, которую создала ранняя версия модели из ветки feat/nlu-module, не содержит колонок recurrence и recurrence_until, и create_all не умеет менять уже существующую таблицу. Функция upgrade_schema поэтому добавляет эти колонки через ALTER TABLE, и тест test_upgrade_legacy_database показывает, что после такого обновления старые записи находятся поиском и проходят проверку целостности.

Каждое соединение с SQLite получает четыре настройки PRAGMA, которые задаёт файл backend/storage/sqlite.py. Настройка foreign_keys включает внешние ключи, которые SQLite по умолчанию не проверяет, а настройка journal_mode=WAL позволяет читать базу, пока другой запрос пишет в неё. Документация SQLite в описании PRAGMA synchronous указывает, что в режиме WAL с synchronous=NORMAL зафиксированная транзакция может пропасть только при отключении питания или сбое операционной системы, поэтому падение или перезапуск процесса данные не теряет.

## Репозиторий записей

Класс RecordRepository принимает сессию SQLAlchemy и делает commit после каждого изменения, поэтому сервис сразу получает запись с присвоенным id. Его публичные методы перечислены в таблице ниже.

| Метод | Что делает |
|---|---|
| create(rec, recurrence=None, recurrence_until=None) | создаёт запись со статусом pending |
| create_many(items) | создаёт много записей одной транзакцией |
| get(id, user_id=None), get_by_id(...) | возвращает запись или None, а при переданном user_id скрывает чужие записи |
| list(user_id, from_, to, record_type, status, limit) | возвращает записи пользователя по возрастанию даты |
| list_by_period(start, end, ...) | возвращает записи с датой внутри отрезка, включая обе границы |
| list_undated(user_id) | возвращает задачи без срока |
| latest(user_id, record_type) | возвращает последнюю созданную запись, на которую ссылаются фразы вида "перенеси её" |
| update(id, RecordUpdate) | меняет только переданные поля |
| update_status(id, status) | отмечает запись выполненной или отменённой |
| set_recurrence(id, rule, until) | включает или выключает повтор |
| delete(id) | удаляет запись, и её вектор удаляется каскадом |
| find_conflicts(dt, window_minutes, user_id, exclude_id) | ищет неотменённые встречи, которые начинаются не дальше window_minutes от dt |

Сигнатуры методов create, get, list, update, delete и find_conflicts совпадают с теми, которые вызывает TaskService из ветки feat/nlu-module. Остальные методы только добавляют возможности, поэтому сервисный слой не требует правок.

## Поиск

Поиск состоит из двух источников, и второй источник включается только по настройке. Основной источник использует FTS5, а дополнительный источник сравнивает векторы, которые строит модель sentence-transformers.

### Полнотекстовый поиск FTS5

SQLite FTS5 не знает русской морфологии, поэтому слово "договору" не совпало бы со словом "договор" в базе. Функция stem из backend/storage/text.py отрезает от слова запроса одно окончание из списка, если после этого остаётся основа от трёх букв, а запрос к FTS5 ищет эту основу как префикс. Например, запрос "договору" превращается в выражение "договор"*, которое находит слова "договор", "договора" и "договором".

Функция build_query из backend/storage/fts.py строит выражение MATCH в четыре шага, и порядок шагов важен, потому что каждый шаг дополняет результат предыдущего.

1. Функция keywords убирает из запроса служебные слова и команды ассистента, такие как "найди", "про" и "задачу", а если запрос состоит только из них, она оставляет все слова.

2. Для каждого оставшегося слова функция берёт основу и основы его синонимов из групп SYNONYM_GROUPS, поэтому запрос "контракт" ищет ещё и "договор".

3. Функция просматривает словарь индекса и добавляет слова, которые содержат основу внутри себя, поэтому запрос "билеты" находит слово "авиабилеты", которое префиксный поиск пропустил бы.

4. Функция добавляет слова словаря, которые отличаются от слова запроса на одну или две буквы, и для этого она использует SequenceMatcher с порогом похожести 0.8, поэтому запрос "презинтация" находит "презентацию".

Каждый вариант попадает в выражение MATCH в двойных кавычках, а варианты соединяются через OR. Кавычки защищают запрос от синтаксиса FTS5, и тест test_fts_syntax_in_query_is_safe показывает, что запросы со словами OR и NEAR, со звёздочкой и с фрагментом SQL-инъекции не ломают поиск.

FTS5 возвращает до пятидесяти кандидатов, а затем репозиторий сортирует их по оценке, которая складывается из четырёх слагаемых. Слово запроса, которое найдено без синонимов, даёт 3 балла, каждое покрытое слово запроса даёт ещё 2 балла, совпадение в заголовке даёт 1 балл, а встроенная функция bm25 добавляет до 1 балла. Такая оценка нужна, потому что bm25 одинаково оценивает точное слово и синоним, тогда как пользователь ожидает увидеть первым точное совпадение, и тест test_exact_word_ranks_above_synonym проверяет это поведение.

Токенизатор unicode61 считает буквы "ё" и "е" разными, и опыт с базой, который мы провели перед выбором схемы, показал, что настройка remove_diacritics на кириллицу не влияет. Триггеры поэтому записывают в индекс копию текста, в которой "ё" заменена на "е", а запрос проходит ту же замену, и тест test_yo_in_stored_text проверяет, что запрос "отчет" находит запись "Сдать квартальный отчёт".

### Семантический поиск на эмбеддингах

Семантический поиск включается переменной SEARCH_EMBEDDINGS=1 и требует пакетов из файла requirements-search.txt. По умолчанию проект использует модель cointegrated/rubert-tiny2, которая весит около 120 МБ и обучена на русских текстах, и тест test_real_model показывает, что она находит нужную запись среди первых трёх результатов во всех четырёх проверочных запросах. Если пакет не установлен или модель не загрузилась, функция get_default_embedder пишет предупреждение в лог и возвращает None, а поиск продолжает работать на одном FTS5.

Векторы считаются лениво перед поиском, поэтому создание записи не ждёт модель, а записи из сидов тоже получают векторы при первом поиске. Метод sync_embeddings пересчитывает вектор только тогда, когда хеш текста или имя модели не совпадают с сохранёнными, и тест test_embeddings_are_cached_and_refreshed это проверяет.

Результаты двух источников объединяются методом Reciprocal Rank Fusion, при котором запись на месте k каждого списка получает 1 / (60 + k) баллов. Этот метод не требует приводить оценки bm25 и косинусного сходства к одной шкале, поэтому запись, которую нашли оба источника, поднимается выше записи, которую нашёл только один источник.

## Повторяющиеся записи

Повторяющаяся запись хранится одной строкой, в которой datetime означает первый повтор, а recurrence задаёт правило. Метод list_by_period вычисляет повторы внутри запрошенного периода и возвращает их как несохраняемые копии записи с тем же id, поэтому команда "отмени стендап" меняет всю серию. Если задана только нижняя граница периода, как во вкладке "Предстоящие" фронтенда, серия даёт один ближайший повтор, а не бесконечный список. Метод find_conflicts тоже учитывает повторы встреч, и тест test_recurring_meeting_conflicts показывает, что еженедельная планёрка конфликтует с новой встречей через три недели.

Правило monthly для 31 января даёт 28 февраля, 31 марта и 30 апреля, потому что функция _add_months берёт последний день месяца, когда исходного числа в месяце нет. Тест test_monthly_clamps_to_month_end проверяет именно эту последовательность.

## Индексы и скорость запросов

Каждый индекс таблицы records соответствует конкретному запросу репозитория, и тест test_queries_use_indexes проверяет через EXPLAIN QUERY PLAN, что SQLite выбирает нужный индекс.

| Индекс | Запрос, который он ускоряет |
|---|---|
| ix_records_user_datetime (user_id, datetime) | выборка за период, например "что у меня сегодня" |
| ix_records_user_type_datetime (user_id, type, datetime) | выборка по типу за период и поиск конфликтов встреч |
| ix_records_user_status (user_id, status) | фильтр невыполненных задач |
| ix_records_user_created (user_id, created_at) | последняя созданная запись |
| ix_records_recurring (user_id, datetime) WHERE recurrence IS NOT NULL | повторяющиеся записи, этот частичный индекс содержит только их |

Мы измерили скорость на базе из 50 000 записей двадцати пользователей на процессоре Apple M2 и взяли медиану из пятидесяти запусков. Выборка за неделю заняла 0.9 мс с индексами и 13.8 мс без них, а поиск конфликтов занял 0.5 мс с индексами и 13.6 мс без них, поэтому индексы ускорили эти запросы примерно в 15 и 27 раз. Поиск по фразе "договор с дизайнером" сначала занимал 795 мс, потому что функция build_query сравнивала слово запроса с каждым словом словаря через SequenceMatcher. Мы убрали из словаря числа и слова короче четырёх букв и добавили быстрые проверки длины и верхней оценки похожести перед полным расчётом, после чего поиск стал занимать 77 мс. В этом замере каждое слово запроса встречается примерно в 20% записей, тогда как у одного пользователя голосового ассистента записей обычно сотни, а не десятки тысяч.

## Сохранность данных и проверка целостности

Тест test_data_persists_across_restart сохраняет запись в файл SQLite, закрывает все соединения, создаёт новый движок на тот же файл и находит запись поиском, поэтому он моделирует перезапуск контейнера. Файл docker-compose.yml монтирует каталог ./data в контейнер, и база в этом каталоге переживает пересборку образа.

Функция check_integrity из backend/storage/integrity.py выполняет PRAGMA integrity_check и PRAGMA foreign_key_check, затем ищет записи с недопустимыми значениями и сверяет индекс FTS5 с таблицей records. Встреча без даты считается ошибкой данных, потому что NLU-модуль в таком случае задаёт уточняющий вопрос о времени и не должен сохранять встречу. Скрипт seed_demo.py с флагом --check печатает отчёт этой функции и завершается с кодом 1, если отчёт нашёл проблему, поэтому его можно запускать перед демо.

## Демонстрационные данные

Модуль backend/storage/demo_data.py создаёт 23 записи, и все даты в нём считаются от момента запуска, поэтому вопрос "что у меня сегодня" во время показа никогда не получает пустой ответ. Набор содержит все примеры фраз из задания, старые записи для поиска про презентацию, Ивана и договор, повторяющийся стендап по будням, ежемесячную оплату аренды, задачу без срока и одну запись второго пользователя. Тест test_demo_covers_task_scenarios проверяет, что выборки на сегодня, на завтра и на неделю содержат записи, которые ожидают сценарии задания.

Скрипт запускается из корня проекта одной из трёх команд, и первая из них пересоздаёт демо-набор в базе из переменной DB_PATH.

    python scripts/seed_demo.py
    python scripts/seed_demo.py --keep
    python scripts/seed_demo.py --check --db ./data/sqlite.db

## Тесты

Тесты слоя данных лежат в шести файлах, и общий файл tests/conftest.py создаёт для каждого теста базу SQLite в памяти, поэтому тесты не зависят друг от друга.

| Файл | Что проверяет |
|---|---|
| test_record_repository.py | создание, чтение, выборку за период с границами, фильтры, изменение статуса, удаление, конфликты и ограничения CHECK |
| test_fts_search.py | запросы из задания, падежи, синонимы, опечатки, букву "ё", ранжирование и синхронность индекса |
| test_semantic_search.py | хранение векторов, их обновление и объединение источников, а также настоящую модель |
| test_recurrence.py | правила повторов, развёртку серии, ближайший повтор и конфликты повторяющихся встреч |
| test_storage.py | схему, идемпотентность init_storage, перезапуск, обновление старой базы, индексы и скорость |
| test_demo_data.py | повторную загрузку сидов, покрытие сценариев и целостность демо-набора |

Тесты запускаются командой ниже, а тесты с настоящей моделью требуют пакетов из requirements-search.txt и переменной RUN_MODEL_TESTS=1, потому что на процессоре Apple M2 эти тесты вместе с загрузкой модели шли 19 секунд, тогда как остальные тесты идут около 3 секунд.

    pytest -q
    RUN_MODEL_TESTS=1 pytest -q tests/test_semantic_search.py

На ветке alexasadullin проходят 77 тестов, а 4 теста с настоящей моделью пропускаются без RUN_MODEL_TESTS=1. С этой переменной и установленной моделью rubert-tiny2 проходят все 81 тест, и модель находит запись "Записаться к стоматологу" по запросу "когда я собирался к зубному", в котором нет ни одного общего слова с записью.

## Подключение к другим веткам

Мы проверили пробное слияние ветки alexasadullin с веткой feat/nlu-module во временном рабочем каталоге. Git сообщил о конфликтах в четырёх файлах, потому что ветка NLU тоже заполнила пустые заготовки слоя данных. После разрешения конфликтов по порядку ниже прошли все 166 тестов объединённой ветки, включая тесты test_repo.py, test_search.py, test_services.py и test_e2e.py из ветки NLU.

1. В файлах backend/models/record.py, backend/repositories/record_repo.py и backend/repositories/search_repo.py нужно оставить версию из ветки alexasadullin командой git checkout --ours, потому что она совместима с вызовами TaskService.

2. В файле backend/db.py функция init_db должна импортировать обе модели и вызвать init_storage, как показывает фрагмент ниже.

        def init_db() -> None:
            from backend.models import Record, Message  # noqa: F401
            from backend.storage import init_storage

            init_storage(engine)

Файл backend/schemas/record.py в ветке alexasadullin совпадает с версией из ветки NLU байт в байт, поэтому он сливается без конфликта. Это исправление было необходимо, потому что в исходной заготовке поле datetime перекрывало одноимённый тип, и pydantic принимал в этом поле только None. Ветки feat/frontend-nikita и feat/voice-module не затрагивают файлы слоя данных, поэтому слияние с ними конфликтов не даёт.

## Что можно улучшить

Ручной список окончаний ошибается на словах с беглой гласной, поэтому основа слова "звонка" не совпадает со словом "звонок", и сейчас эту ошибку исправляет только поиск опечаток. Морфологический анализатор pymorphy3 привёл бы слова к начальной форме, и тогда индекс мог бы хранить леммы вместо исходных слов. Векторы сейчас сравниваются перебором в Python, что подходит для сотен записей пользователя, однако при десятках тысяч записей стоит перейти на расширение sqlite-vec, которое выполняет поиск ближайших векторов внутри SQLite.
